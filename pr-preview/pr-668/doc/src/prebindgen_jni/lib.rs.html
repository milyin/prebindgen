1//! JNI / Kotlin language adapter — the [`JniGenBuilder`] back-end.
2//!
3//! Sibling of the C adapter (now the separate `prebindgen-c` crate): it implements the
4//! language-agnostic [`prebindgen_registry::Prebindgen`] trait to
5//! turn a flat `#[prebindgen]` library into a Rust file of JNI `extern "C"`
6//! wrappers plus a fan-out of generated Kotlin sources.
7//!
8//! Pipeline:
9//!   1. [`prebindgen_registry::Registry::builder`] describes a binding over a model built from
10//!      `(syn::Item, SourceLocation)` (typically `source.items_all()`).
11//!   2. `Registry::write_rust` resolves every
12//!      required type via a configured [`JniGenBuilder`] and writes the generated
13//!      Rust bindings file.
14//!   3. `JniGenBuilder::write_kotlin` walks the resolved registry to emit the
15//!      secondary Kotlin artifacts (typed-handle classes, data/enum classes,
16//!      exception classes, the centralized `JNINative` holder).
17//!
18//! # The raw-pointer surface is not part of the consumer API
19//!
20//! Generated Kotlin passes native pointers around as `Long`s, and generated
21//! native code dereferences them. A `Long` a consumer made up therefore has to
22//! be unable to reach that code (prebindgen#37) — from Kotlin **and** from
23//! Java, which is a separate problem: `internal` and `@RequiresOptIn` are
24//! Kotlin-source constructs, and an `internal` member compiles to a *public*
25//! JVM member under a mangled name that javac will happily call.
26//!
27//! So each entry point carries `@JvmSynthetic`, which sets `ACC_SYNTHETIC` —
28//! javac refuses to resolve it, while JNI (which looks up by name) and the
29//! JVM's native-method binding do not care:
30//!
31//! * **Handle constructors are `private`**, behind an `internal`
32//!   `@JvmSynthetic fromRawPtr` factory. `@JvmSynthetic` cannot target a
33//!   constructor at all, and `internal` alone still left
34//!   `new KeyExpr(0xdeadbeefL)` compiling from Java. Nothing on the Rust side
35//!   constructs a handle, so this costs no generated call site.
36//! * **Every `external fun` is `@JvmSynthetic`**, as is each class's static
37//!   `freePtr`. `internal object JNINative` is a public JVM class with a
38//!   public `INSTANCE`, so its externs were callable directly — the handle
39//!   layer bypassed entirely.
40//! * **`NativeHandle.peek()` and the `fromParts` factories** are looked up
41//!   from Rust by JNI reflection (`call_method` / `call_static_method`), so
42//!   their names must survive. They get `@JvmSynthetic` plus
43//!   **`@UnsafeNativeApi`**, a generated `@RequiresOptIn` annotation class in
44//!   the base package, which is what constrains a *Kotlin* consumer.
45//! * **Internal state — `ptr`, `markConsumed`, the locking helpers — is
46//!   `@JvmSynthetic` too.** A visible `setPtr$module` would let a Java caller
47//!   repoint a live handle and have the next generated call free that address.
48//!
49//! The base `NativeHandle` constructor stays `internal`, because the generated
50//! subclasses reach it through `super`. A Java subclass is inert: every
51//! generated signature takes a `final` concrete handle type, and there is
52//! nothing left for it to call.
53//!
54//! Every generated file carries `@file:OptIn(<pkg>.UnsafeNativeApi::class)`:
55//! generated code is the trusted producer of these pointers. Consumer code
56//! gets no such blanket and must opt in per declaration, which is the point.
57//!
58//! The marker lives in the base package and is named fully qualified. With no
59//! base package configured it would land in the root package, which Kotlin
60//! cannot import from a subpackage — `write_kotlin` refuses that combination
61//! rather than emit an unguarded surface.
62//!
63//! # Fixed-width unsigned integers
64//!
65//! JniGenBuilder exposes Rust's fixed-width unsigned scalars without narrowing their
66//! domain at the Kotlin boundary:
67//!
68//! | Rust | Kotlin surface | JNI wire |
69//! |------|----------------|----------|
70//! | `u8` | `Int` | `jint` |
71//! | `u16` | `Int` | `jint` |
72//! | `u32` | `Long` | `jlong` |
73//! | `u64` | `ULong` | `jlong` / `Long` bit pattern |
74//!
75//! Inputs for `u8`, `u16`, and `u32` are range-checked and report a
76//! [`JniBindingError`] through the generated binding-error handler. `u64`
77//! uses Kotlin's bit-preserving `ULong.toLong()` / `Long.toULong()` bridge.
78//! These mappings compose through nullable/result outputs, generated data
79//! classes, callbacks, const getters, and supported output collections.
